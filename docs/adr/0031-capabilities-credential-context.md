# ADR 0031: Explicit credential context in server capabilities

## Status

Accepted.

## Context

OmniWA accepts a global admin key and per-instance bearer tokens through the
same `apikey` header. Console previously discovered the credential tier by
calling the admin-only `GET /instance/all` route and treating its expected 401
or 403 response as control flow before probing an instance route. This creates
noise in browser diagnostics, access logs, and authentication monitoring.

Clients cannot safely infer authority from credential syntax or capability
entries. Capability entries describe deploy-time features and projection
readiness, not the authentication decision. The credential context must come
from the boundary that validated the bearer secret.

`GET /server/capabilities` already accepts both credential tiers and is the
existing client-negotiation endpoint. Adding another authentication-context
endpoint would duplicate authentication and require another request without
providing a distinct ownership boundary.

## Decision

Extend `GET /server/capabilities` additively with a required
`credentialScope` field whose closed values are `admin` and `instance`.
Instance-authenticated responses also contain `instanceId`; admin responses
omit it.

Authentication middleware records a typed principal containing only the scope
and, for an instance credential, the stable instance UUID. The capabilities
handler reads this principal directly. It never infers scope from capabilities,
projection state, credential format, or provider data.

The instance UUID is generated by OmniWA, persists across credential rotation,
and is already exposed by public instance-management DTOs. It is not a phone
number, WhatsApp JID/LID, or provider identifier. No bearer credential, lookup
digest, storage metadata, or provider identity is included in the principal or
response.

Projection readiness continues to control only projection-dependent capability
entries. Syncing, stale, not-started, and ready-with-no-feature states can all
return HTTP 200 for a valid credential. Projection storage failures remain
HTTP 500 because silently substituting a capability set would change existing
negotiation semantics. HTTP 401 is reserved for a missing or invalid
credential; credential lookup infrastructure failures are not presented as
authentication rejection.

## Alternatives

### Add `GET /auth/context`

Rejected. It would duplicate an authentication surface and client request even
though the existing capabilities route already authenticates both tiers and is
the established negotiation boundary.

### Publish scope as a capability

Rejected. Capabilities are configuration- and readiness-dependent. Encoding
authority there would couple authentication to projection behavior and invite
inference from an open-ended string list.

### Infer scope from key format or failed admin probes

Rejected. Key syntax is not a public authorization contract, and expected 401
responses pollute security signals and operational monitoring.

## Consequences

- Existing clients remain compatible because all existing fields and
  capability semantics are unchanged.
- New clients discover the credential tier in one successful request.
- The `admin` and `instance` values become a long-lived closed public enum.
- Swagger 2.0 cannot express the conditional requirement on `instanceId`; the
  schema marks it optional and the handler plus contract tests enforce that it
  is present exactly for instance credentials.
- Authentication context becomes typed while legacy Gin instance context is
  retained for existing business handlers.

## Rollout and rollback

Deploy the additive backend first. Console then prefers `credentialScope` and
temporarily falls back to its legacy sequential probe only when the field is
absent. After the minimum backend revision is deployed everywhere, Console may
remove the fallback in a separate change.

Before that Console cleanup, rolling back the backend is safe because the
client still understands the old response. After cleanup, rollback requires
restoring a backend revision that exposes this contract or temporarily
restoring the Console fallback. There is no database migration, backfill,
destructive operation, or feature flag associated with this change.
